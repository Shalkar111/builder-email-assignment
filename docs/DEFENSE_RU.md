# Подготовка к защите

## Объяснение примерно на минуту

Я выбрал продукт Email. Письмо состоит из отправителя, получателя, темы и текста.
Интерфейс EmailBuilder задаёт четыре шага сборки. Их реализуют два класса:
EmailObjectBuilder создаёт объект Email, а EmailPreviewBuilder создаёт строку
с предпросмотром. Director содержит два готовых рецепта: приветственное письмо
и подтверждение заказа. Один рецепт подходит обоим строителям, потому что
Director работает через интерфейс.

Каждый шаг возвращает this, поэтому методы можно соединить в цепочку. Когда
вызывается getResult(), строитель проверяет данные. Если обязательного поля
нет или адрес неправильный, возникает IllegalStateException с понятным текстом.
Готовый Email неизменяемый: класс final, поля private final, сеттеров нет.
Конструктор доступен только внутри пакета и копирует значения из черновика.

## В каком порядке показать код

1. `Email.java`: продукт и неизменяемость.
2. `EmailBuilder.java`: четыре общих шага.
3. `EmailObjectBuilder.java`: `return this`, проверка, результат Email.
4. `EmailPreviewBuilder.java`: те же шаги, результат String.
5. `EmailDirector.java`: два рецепта, параметр типа интерфейса.
6. `Main.java`: один рецепт вызывается с разными строителями.
7. `EmailDraft.java`: общая проверка данных.
8. Запуск `Main`, затем `BuilderChecks` или `./test.sh`.

## Частые вопросы

**Зачем Builder, если можно вызвать конструктор?**
Он отделяет последовательность сборки от представления результата, позволяет
собирать объект по шагам и переиспользовать готовые рецепты. Для четырёх полей
конструктор тоже возможен; здесь Builder демонстрирует требуемый паттерн и две
разные формы одного письма.

**Где здесь два представления?**
`Email` и `String`. Это одинаковые данные письма, но объект можно использовать
в Java-коде, а строку удобно читать. Text builder сам формирует строку из
черновика, а не просто вызывает `toString()` готового Email.

**Почему getResult() отсутствует в интерфейсе?**
Результаты разного типа. Director нужны только общие шаги. Client знает конкретный
строитель и получает результат нужного типа. Можно было бы использовать generic
интерфейс, но для задания выбран вариант из примера преподавателя.

**Что делает return this?**
Возвращает тот же экземпляр строителя. После `setFrom(...)` можно сразу вызвать
`setTo(...)`. В реализации возвращается конкретный тип строителя: это допустимое
уточнение возвращаемого типа метода интерфейса, то есть covariant return type.

**Зачем Director?**
Он хранит готовые рецепты и порядок шагов. Новый строитель с тем же интерфейсом
сможет использовать эти рецепты без изменения Director. Director не обязателен
для ручной сборки письма.

**Почему Email неизменяемый, а строитель изменяемый?**
Состояние строителя нужно менять в ходе сборки. Продукт должен сохранить уже
полученный результат. Email копирует четыре String, не хранит ссылку на EmailDraft,
не имеет сеттеров, а String тоже неизменяемый.

**Почему одного final недостаточно для неизменяемости?**
final запрещает переназначить поле, но не запрещает менять содержимое списка или
другого изменяемого объекта. Здесь поля String, поэтому такой проблемы нет. Для
списка вложений понадобилась бы защитная копия, например `List.copyOf(...)`.

**Зачем EmailDraft?**
В нём собраны временные значения и единые правила проверки. Каждый строитель
создаёт собственный экземпляр. Без helper-класса пришлось бы дублировать правила
и следить, чтобы они не расходились. Класс и поля доступны только внутри пакета.

**Когда срабатывает проверка?**
При каждом `getResult()`. Промежуточный черновик может быть неполным. Обязательны
все четыре поля; адреса проходят простую проверку формата, тема должна быть в одну
строку, текст может занимать несколько строк.

**Почему IllegalStateException?**
В момент получения результата состояние строителя некорректно. Сообщение
указывает поле, например `To is required`.

**Что будет при повторном использовании строителя?**
Новый set-метод заменит старое значение. getResult() не очищает черновик. Оба
рецепта Director задают все поля, поэтому старые значения не протекают между
готовыми конфигурациями. Ранее созданные Email и String не меняются.

**Какие принципы Clean Code использованы?**
Понятные имена; одна ответственность у класса; зависимость от интерфейса;
единая проверка без дублирования; инкапсуляция и неизменяемость; понятные ошибки;
короткие fluent-методы. Настройки рецептов и текстовый шаблон вынесены в именованные
константы. В PDF есть реальные фрагменты каждого примера.

**Чего эта программа не делает?**
Не отправляет почту, не подключается к SMTP и не проверяет существование адреса.
Проверка адреса учебная, а не полная реализация стандарта email. Строители не
предназначены для одновременной работы из нескольких потоков.

## Что потренировать самостоятельно

Измени тему в рецепте и запусти программу. Собери письмо вручную цепочкой методов.
Убери `setTo(...)` у нового строителя и объясни ошибку. Покажи, где нужно добавить
третий рецепт и почему для него не требуется переписывать строители.
